## Reproducir estructura sin datos privados

1. Crear un proyecto de desarrollo vacío controlado, sin conectar producción.
2. Revisar y aplicar en orden los SQL de [supabase/migrations](../../supabase/migrations), mediante Supabase CLI o SQL editor de ese proyecto. Conservar historial y ejecutar advisors después. No ejecutar `db reset` sobre remoto ni seeds.
3. Las migraciones históricas de catálogo usan `brand`; el proyecto real heredado usa `marca`. Node detecta ambos mediante `server/product-schema.js`; el Worker oficial está fijado a `marca` para el proyecto esperado. No reutilizar sin adaptar esa configuración en un proyecto nuevo. Esta diferencia está documentada, no se oculta como dump idéntico de producción.
4. Verificar tablas, grants, RLS y operaciones con cuentas de desarrollo. Crear datos sintéticos manualmente por el flujo normal/Admin, sin exportar clientes ni promover cuentas desde el navegador.

`supabase/schema.sql` es un esquema histórico, no la fuente canónica completa actual. El esquema real de columnas y las migraciones posteriores tienen prioridad. La reproducción conectada en proyecto nuevo no fue ejecutada en esta tanda y figura pendiente en la matriz.

# Límite de 40 líneas

El límite vigente es **40**, no 20. Se usa Acorn 8.15.0 fijado en desarrollo y el lockfile. Ejecutar desde la raíz, también dentro de una extracción sin `.git`:

```sh
corepack pnpm install --frozen-lockfile
corepack pnpm run check:functions
node scripts/function-inventory.mjs . --write
```

El [JSON](inventario-funciones.json) incluye archivo, nombre inferido, tipo, línea inicial/final y cantidad. Se cuentan líneas físicas inclusivas de declaración a cierre: comentarios y blancos internos incluidos. Las funciones anónimas, callbacks, métodos, getters, setters y constructores se identifican por AST, sin comprimir instrucciones para bajar el conteo. HTML inline JavaScript también se analiza; JSON-LD se excluye por ser datos.

Alcance: todos los JS/MJS/CJS y HTML propios encontrados recursivamente, incluidos servidor, navegador, Workers, Pages, scripts y tests. Se excluyen dependencias y salidas generadas: `node_modules`, `.git`, `dist`, `.wrangler`, `coverage`, `.pnpm-store`; no se siguen symlinks. No se utiliza `git ls-files`. SQL y CSS no contienen funciones JavaScript y no forman parte de este contador; sus estructuras se documentan aparte.

Programa principal: `start` en Node, `fetch` del Worker y los inicializadores de navegador se cuentan como funciones. Cada bloque ejecutable superior explícito (`if`, bucles, `try` y bloques) se cuenta también con su rango físico. Un módulo con muchas declaraciones no es un único bloque principal: imports, clases, constantes de datos y registros de callbacks se mantienen como declaraciones y sus funciones se cuentan individualmente. No se atribuye al archivo entero una función ficticia. Esta interpretación está explicitada para revisión del profesor, no como aceptación acreditada.

Refactorizaciones: construcción de Express dividida en contexto e instaladores ordenados de middleware/rutas; perfil y sesión conservan autorización; configuración Node y Workers separada del arranque; checkout separado en carga, cupón, pago y eventos; instalación de simulación académica separada de firma; wrappers de helpers convertidos en declaraciones con API pública conservada. Se ajustaron también fixtures extensos sin quitar assertions.

# Documentación técnica DREAMS

## Arquitectura

El frontend multipágina vive en `public/` y consume una API REST Express bajo `/api`. El servidor usa `@supabase/supabase-js` para Postgres y Supabase Auth. Las sesiones se mantienen en cookies HTTP-only de acceso y renovación; el carrito permanece en `localStorage` y no es una orden ni un pago.

La definición versionada de datos está en `supabase/migrations/`. `supabase/schema.sql` es sólo un snapshot legacy y no debe usarse como fuente de despliegue.

## Datos y seguridad

Las tablas activas son `profiles`, `products`, `reviews` e `inquiries`. `favorites` se conserva vacía como estructura histórica protegida por RLS, pero ya no tiene interfaz ni API. La baseline declara claves foráneas, índices, triggers y RLS. La aplicación de servidor usa una clave secreta de Supabase; esa clave jamás debe exponerse al navegador.

Helmet aplica CSP, las escrituras sensibles requieren sesión/rol, auth y consultas tienen rate limit, y los datos dinámicos se escapan antes de insertarse en HTML. Los roles se leen de `profiles.role`, no de metadata controlable por el usuario.

# Manual de uso DREAMS

## Usuario

1. Abrir la URL del entorno (en local, `http://localhost:3000`).
2. Entrar a `Perfumes`.
3. Buscar por nombre, marca o familia.
4. Filtrar por marca, género o tipo.
5. Abrir cualquier perfume.
6. Revisar notas de salida, corazón y fondo.
7. Revisar intensidad.
8. Agregar el producto al carrito.
9. Iniciar sesión para publicar opiniones o acceder al panel si la cuenta es administradora.
10. Abrir el carrito para modificar cantidades o eliminar productos.
11. Consultar el carrito o un perfume por WhatsApp.

## Registro

En `Mi cuenta`, seleccionar `Registrarme`, completar nombre, correo y contraseña.

## Administrador

1. Iniciar sesión con el correo administrador.
2. Desde la cuenta aparecerá `Entrar al panel de administrador`.
3. El panel permite crear, editar y eliminar productos.
4. Las modificaciones se guardan en Supabase mediante la API del servidor.
5. Volver a la tienda para comprobar el cambio.

## WhatsApp
